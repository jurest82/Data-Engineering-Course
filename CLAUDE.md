# CLAUDE.md: Data Engineering Course

## What this project is

Batch data pipeline that ingests traffic accident reports, uploaded as an Excel file, for the traffic monitoring service described in `README.md`. This document covers the **batch** flow, the traffic sensor **streaming** flow, and the **ETL** that copies both into RDS PostgreSQL (all three complete, see their own sections).

## How to work in this repository

Nothing from this project is installed directly on the host. All work on `backend` and `infrastructure` (installing dependencies, running the `aws` CLI, the `serverless` CLI, formatting/linting Python, deploying) happens by spinning up that subproject's Docker container (`docker compose`, using that subproject's `.docker/docker-compose.yml`) and running it there, replicating what its `entrypoint.sh` does (git configuration, `npm install`, AWS credentials from `.envs/`).

**Claude never runs deploys, `git push`, migrations against a deployed database, or other destructive/state-changing commands.** Give the command (or a read-only diagnosis, e.g. `serverless print`/`package`) and let the developer run it themselves.

## Monorepo structure

- **Root**: devcontainer for monorepo-level work (e.g. generating the architecture diagrams). `.docker/Dockerfile` is multi-stage: `img-base` (Python 3.13 + Node 24 + common tools, includes `~/.cfnlintrc` so `cfn-lint` ignores the W3005 false positive that Serverless Framework adds) → `img-backend` (adds `boto3`, only so the local linter/autocomplete resolves the imports; the Lambda runtime already includes it, it's never packaged) / `img-infrastructure` (no additional differences for now) / `img-root` (adds `graphviz` + the Python `diagrams` library, used to generate the architecture diagrams in `docs/` — one per pipeline, see `docs/architecture.py` — not specific to `backend` or `infrastructure`, that's why it lives in the root image).
- **`backend/`**: contains **several Serverless Framework stacks, each in its own folder under `backend/serverless/<stack>/`** (same pattern as `infrastructure/serverless/<stack>/`), not a single stack for the whole backend:
  - `backend/serverless/layers` (`service: backend-layers`): only the shared Lambda Layers, no functions of its own. **Must be deployed first**, since the other `backend` stacks consume its ARNs via SSM.
  - `backend/serverless/batch` (`service: backend-batch`): API Gateway + the batch flow's 3 Lambdas + their IAM roles.
  - Lambda code in `backend/src/<function_name>/`, in **Python**, formatted with `yapf` + `isort` (see `pyproject.toml`); logic shared between Lambdas in `backend/src/common/`. Since each `serverless.yml` lives two levels below `backend/` (`backend/serverless/<stack>/`), each function's `package.patterns` references its code with `../../src/...`. `handler.py` files carry no module-level docstring (unlike scripts under `backend/database/`, which do) — keep them lean.
  - **`backend/src/__init__.py`** (and one in every `src/<function_name>/`) exists purely so `pylint`'s own package-boundary heuristic resolves `from src.common import ...` — not needed at runtime (Python's implicit namespace packages already resolve it without it). This has proven sensitive to `pylint`'s own version: a routine `pip3 install pylint` (installed unpinned in the Dockerfile) once picked up a newer release that broke this resolution project-wide (`E0401: Unable to import 'src...'` on every handler, not just new code) until `src/__init__.py` was added back. If that error reappears everywhere at once after a container rebuild, suspect a `pylint` version regression before assuming the code broke.
  - **Python dependencies go through Lambda Layers, not through a `requirements.txt` packaged in each function.** Each layer lives in `backend/src/layers/<name>/` (with its own `requirements.txt` and a `.gitignore` that ignores the generated `python/` folder) and is defined in `backend/serverless/layers/layers.yml` with `path: ../../src/layers/<name>` + `package.patterns: ['!./**', 'python/**']`. Since the layers live in a separate stack, functions in the other `backend` stacks reference them by ARN via SSM (`layers: [${ssm:/${env:DEPLOY_APP}-backend-layers/<Name>LayerArn}]`), not with a direct `!Ref`. `backend`'s `entrypoint.sh` installs those dependencies into `src/layers/<name>/python/` and generates a `.pth` file in the container so they also work for local testing.
  - **Why not `module:`**: the Python-requirements integration's `module` option (for a per-function `requirements.txt`) changes the zip's effective root to the function's folder, which clashes with `package.patterns` (which keeps resolving paths relative to where `serverless.yml` lives) and with having shared code (`common/`) outside that folder; with that combination the packaging ends up inconsistent and includes no files at all. Lambda Layers avoid the problem entirely (they have their own `path:` mechanism for the root).
  - **Current layers**: `Commons` (`openpyxl`), `Mongo` (`pymongo`), `Security` (`cryptography`), `Postgresql` (`psycopg2-binary`, for the RDS ETL — see "ETL pipeline architecture"). Each Lambda only references the layers it actually needs (e.g. Lambda 1/2 don't load `Mongo` or `Security`).
  - **Secrets referenced by name, not by ARN**: `custom.secretsManager.<name>` builds the secret's name directly (e.g. `/${env:DEPLOY_APP}-secrets/MongoCredentials`, matching how `infrastructure` names it), without looking up the ARN via SSM. IAM does need an ARN, though, so it's built with a wildcard: `arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:<name>-*` (the `-*` covers the random suffix Secrets Manager adds).
  - **Deploy architecture (`x86_64`/`arm64`) is resolved dynamically**, not by hand: `provider.architecture: ${file(../architecture.js):get}` (a single `architecture.js` shared in `backend/serverless/`, referenced by all 3 stacks), a script that returns Node's `process.arch`. Needed because `pymongo`/`cryptography` ship compiled extensions, which must match the architecture of whoever deploys (relevant because students may be on Apple Silicon Macs or Intel/Windows x86).
  - **Test cases**: `backend/tests/fixtures/batch/` has example Excel files (`valid_report.xlsx`, `missing_column.xlsx`, `invalid_rows.xlsx`, `exceeds_max_rows.xlsx`) and `generate_base64.sh`, which generates a `.json` for each `.xlsx` with the body ready to paste into Postman (`{"file": "<base64>"}`). `backend/tests/fixtures/sensor_readings/` has example MQTT payloads to paste into the IoT Core console's MQTT test client (see its own `README.md`).
- **`infrastructure/`**: shared base resources (Serverless Framework): S3, SQS+DLQ, Secrets Manager, CloudWatch alarms, a PostgreSQL RDS instance, and the ETL pipeline's SQS+DLQ/SNS. Doesn't deploy the Lambdas' IAM roles, that's `backend`'s responsibility. Each resource lives in its own sub-stack (`serverless/storage`, `serverless/queue`, `serverless/secrets`, `serverless/alerts`, `serverless/rds`, `serverless/etl`), deployed independently. `serverless/queue` is deliberately general-purpose, not exclusive to batch: it hosts both `AccidentReports`/its DLQ (batch) and `SensorReadings`/its DLQ (streaming), instead of having a separate queue sub-stack per flow — `serverless/etl` is kept **separate** from `serverless/queue` even though it's also SQS/DLQ, since it's internal ETL plumbing (Generator→Extractor→Dispatcher→SNS→Transformer) rather than a real pipeline's ingestion queue (see "ETL pipeline architecture"). All of them are independent from each other **except `alerts`**, which must be deployed **after** `backend/serverless/batch` (its alarms reference, via SSM, the name of the `SplitAndEnqueue` Lambda that stack exports) — it's the only reversal of the usual infra-before-backend order.
- **`docs/`**: architecture diagrams, one per pipeline (`architecture_batch.png`, `architecture_streaming.png`, `architecture_etl.png`), generated with the Python `diagrams` library from `docs/architecture.py` (run it with `python3 architecture.py` inside the root devcontainer, which brings `graphviz` via `img-root`). Deliberately separate diagrams rather than one combined view: cross-cutting edges (toward Mongo/Secrets Manager, toward the shared alarms) force long curves in Graphviz's auto-layout; split apart, each pipeline is a straight chain. The ETL diagram draws the chain for **one** domain only (labeled "one chain per domain" in the title) — `accidentReports` and `sensorReadings` are structurally identical, so drawing both would just duplicate the same shape twice. Edge labels on the diagonal (non-chain) edges use `xlabel`, not `label`: a `label` on a long diagonal edge reserves inline space that graphviz sometimes renders as a visible gap before the arrowhead reaches the target node; `xlabel` places the text beside the line instead, without breaking it.
- **`frontend/`**: doesn't exist yet, not part of the current scope (see "Open items"); no longer mentioned in `README.md` as if it were part of the monorepo. Until there's one, the batch flow is tested directly against the API (e.g. with Postman). (There's no standalone top-level `etl/` folder either — the ETL pipeline is built, but distributed across `backend/serverless/etl` and `infrastructure/serverless/etl`, same as every other flow in this repo.)
- Each subproject (`backend`, `infrastructure`) has its own devcontainer, `docker-compose.yml`, `entrypoint.sh`, `.envs/config.env` (with `DEVELOPER`, used so deployed resource names don't collide between developers) and `ws.code-workspace` (a multi-root workspace that also exposes the other subproject's `.envs` and the root's shared ones).

## Batch flow architecture

Client sends a `POST` to API Gateway with the accident Excel file encoded in **base64**, max **300 rows** per file, exposed as a REST API (not HTTP API) specifically to get API Gateway's native API Key check (`private: true` + `provider.apiGateway.apiKeys`) rejecting bad requests before the Lambda even runs.

1. **`ValidateAndStore`** (synchronous): validates structure and business rules, rejecting the whole file on any invalid row (nothing saved, 400 with the detail) rather than accepting the valid rows and dropping the rest. Excel columns are in Spanish, mapped to English for the code/Mongo:

   | Excel column                 | Field in code/Mongo    | Validation                                                                                |
   | ---------------------------- | ---------------------- | ----------------------------------------------------------------------------------------- |
   | `fecha` + `hora`             | `occurred_at`          | Combined into a single ISO 8601 timestamp                                                 |
   | `ciudad`                     | `city`                 | Bogotá, Medellín, Cali or Barranquilla                                                    |
   | `via`                        | `road`                 | Non-empty text                                                                            |
   | `severidad`                  | `severity`             | leve/moderado/grave/fatal in the Excel, translated to minor/moderate/severe/fatal on save |
   | `vehiculos_involucrados`     | `vehicles_involved`    | Integer 1-20                                                                              |
   | `nombre_persona_involucrada` | `involved_person_name` | Non-empty text (PII)                                                                      |
   | `cedula_persona_involucrada` | `involved_person_id`   | Numeric, 6-10 digits (PII)                                                                |

   `severity` is translated (leve→minor, moderado→moderate, grave→severe, fatal→fatal) before saving; `city`/`road` aren't (proper nouns). Schema/validation lives in `backend/src/common/accident_reports.py`, reused by the next two Lambdas.
2. **`SplitAndEnqueue`**, triggered by that upload's `ObjectCreated` (scoped to the `uploads/` prefix, or moving the file afterward would re-trigger it): re-parses/re-validates from S3 (Lambda 1 only passed it the raw file, not the parsed rows), splits into one SQS message per row (`source_s3_key`/`row_number` added for traceability), then moves the file to `processed/` or `failed/`. Failing here — re-validating a file Lambda 1 already accepted — is a code bug, not bad data, so it's alarmed as an `Errors` metric (see "Observability"), not routed through a DLQ.
3. **`ValidateAndPersist`** (SQS, batch size 1): re-validates (defense in depth), encrypts `involved_person_name`/`involved_person_id` (Fernet), and persists to MongoDB Atlas (Mongo client and Secrets Manager credentials both cached across warm invocations). On validation failure it self-forwards the row to the DLQ itself (with `validation_errors` attached) instead of letting SQS retry it to exhaustion — invalid data doesn't get fixed by retrying, and the DLQ message keeps the PII in plain text on purpose, so it can be corrected before a redrive. No reserved concurrency, here or anywhere in this project: the free-tier account caps out at 10 concurrent executions total, with none to spare.
4. IAM: one role per Lambda, scoped narrowly per step (S3 write / S3 read+write + SQS send / SQS receive+delete + DLQ send + the Mongo and PII-key secrets).

**Database**: MongoDB Atlas, free tier **M0** (not AWS DocumentDB: no real free tier, and would require putting the Lambdas inside a VPC).

## Streaming flow architecture

Fixed traffic sensors report average speed and vehicle count per road, every few seconds, via MQTT against **AWS IoT Core**: same shape as the batch flow, **IoT Core → SQS → Lambda → MongoDB**, with defense-in-depth validation and self-forward-to-DLQ.

**Why not Kinesis Data Streams**: no real free tier (bills per shard-hour from minute one, regardless of traffic); IoT Core does have a message free tier, and fits the sensors theme besides.

- `infrastructure/serverless/iot`: a **generic IoT Policy**, not tied to a device, using `${iot:Connection.Thing.ThingName}` so a certificate can only connect/publish on its own topic (`sensors/traffic/<thing-name>/data`); a Topic Rule (`SELECT *, topic(3) AS thing_name ...`) stamps the sensor's identity onto the message straight from that trusted topic segment — the sensor's own JSON payload carries no `sensor_id` at all, precisely so there's nothing client-controlled to trust instead.
- `PersistSensorReading` (`backend/serverless/streaming`) sets `sensor_id` from that trusted `thing_name` before validating. No PII in a reading (`city`, `road`, `speed_avg`, `vehicle_count`, `recorded_at`), so no encryption/`Security` layer. Shares `backend/src/common/mongo.py`'s connection-caching helper with batch's Lambda 3.
- Provisioning/testing a real sensor: `backend/tests/sensor_readings/provision_sensor.sh <sensor-id>` (Thing + X.509 cert, idempotent per sensor) and `send_sensor_reading.sh <sensor-id> [file] [topic]` (`mosquitto_pub` with mTLS). Confirmed one sensor's certificate can't publish on another's topic (blocked by the Policy — verified nothing arrived when subscribed to that topic from the console). `mosquitto_pub -i` must match the certificate's Thing name, or the connection drops immediately ("connection was lost").

## Observability

Stack `infrastructure/serverless/alerts`: an SNS topic with an email subscription (`ALERTS_EMAIL`, needs the subscription confirmed the first time the stack is deployed) receives three CloudWatch alarms:

- Visible messages in the accident reports DLQ (`ApproximateNumberOfMessagesVisible >= 1`): indicates rows Lambda 3 couldn't validate/process.
- Errors in Lambda 2 (`SplitAndEnqueue`, `Errors` metric >= 1): indicates it failed re-validating a file Lambda 1 had already accepted, a symptom of a bug in the code itself (see point 2 of the batch flow architecture).
- Visible messages in the sensor readings DLQ (`ApproximateNumberOfMessagesVisible >= 1`, same criterion as accidents'): indicates readings `PersistSensorReading` couldn't validate/process.

There's no alarm on Lambda 1 or Lambda 3 errors: Lambda 1 responds its errors directly to the client via API Gateway (synchronous), and Lambda 3's invalid rows go to the DLQ (already covered by the alarm above) instead of raising an exception. Streaming has no step equivalent to Lambda 2 (IoT Core routes straight to the queue with no intermediate re-validation), so it doesn't have that second "bug in the code" alarm either.

The same stack also defines an **AWS Budget on cost** (`AWS::Budgets::Budget`, USD 1/month, notifies by email on both actual and forecasted spend): unlike the CloudWatch alarms (scoped to this pipeline), the Budget covers spend for **the whole AWS account**, meant to catch anything that fell outside the free tier. "Free Tier Alerts" (a Billing account preference, not an IaC resource, that would warn before any real charge) was deliberately not also turned on: it was considered and dropped as redundant next to the Budget, for this project's scope.

## Database seeding and index migrations

`backend/database/` (not IaC — MongoDB Atlas itself isn't managed by any IaC tool in this project, its M0 cluster is created manually):

- `backend/database/seeders/seed_mongo.py` + `seed.sh`: fills `accidentReports`/`trafficSensorReadings` with realistic synthetic data (`Faker`, plus a small curated list of real road names per city), reusing the real validation (`accident_reports.validate_row`, `sensor_readings.validate_reading`) and PII encryption (`validate_and_persist.pii.encrypt`) so seeded documents are indistinguishable from ones a real device/upload would produce — including `source_s3_key`/`row_number` on accident reports, simulated in batches of up to `MAX_ROWS`, since `SplitAndEnqueue` adds those to every real row too. Feeds the ETL to RDS PostgreSQL (see "ETL pipeline architecture") and, eventually, a Bedrock agent (not yet built). `seed.sh` refuses to run unless the `MongoCredentials` secret's `STAGE` tag is `dev` or `test`, so synthetic data can never land in a real environment by accident. Inserts happen in batches of `INSERT_BATCH_SIZE` (500) rather than one giant `insert_many`: a single call with tens of thousands of documents outlasts what an Atlas M0 (free tier) connection tolerates and gets dropped mid-request.
- `backend/database/migrations/`: index management via the `mongodb-migrations` PyPI package (CLI `mongodb-migrate`). Migration files (`migrations/migrations/<timestamp>_*.py`) implement `mongodb_migrations.base.BaseMigration`'s `upgrade`/`downgrade`, each just calling `create_index`/`drop_index` via the same `mongo.get_collection` helper the Lambdas use. `migrate.sh` resolves the Mongo secret itself (bash + `aws secretsmanager` + `jq`, URL-encoding the password) since it drives the `mongodb-migrate` CLI directly, not Python code; it also exports `PYTHONPATH` to `backend/` first, since `mongodb-migrate` loads each migration file with a raw `__import__()` that otherwise can't resolve `from src.common.mongo import ...` (it runs as an installed console script, not via `python3 -m`). Accepts an optional timestamp as a second argument (passed through as `--to_datetime`, same as the CLI) to upgrade/downgrade only up to a specific migration instead of all of them — without it, `mongodb-migrate` applies or reverts _every_ migration. Applied migrations are tracked in an automatically-created `migrationLogs` collection — the audit trail this pattern is meant to give.
- Current indexes: `accidentReports` on `(city, occurred_at)`, `trafficSensorReadings` on `(sensor_id, recorded_at)` — chosen to match the two most natural query patterns ("accidents in city X, most recent first" / "readings for sensor X, ordered by time").
- `backend/database/demo_indexes.py`: the classroom demo. Always reverts every index first (via `migrate.sh --downgrade`, unconditionally — not an opt-in flag, since a real before/after is the script's only job), then for each collection runs `explain()` before its index exists (`COLLSCAN`), re-applies _only that collection's_ migration (`migrate.sh --upgrade <that migration's timestamp>`, so demoing one collection's index can never side-effect the other's), runs `explain()` again (walking into `inputStage` to find the real `IXSCAN`/`COLLSCAN`, since MongoDB often wraps it in an outer `FETCH` stage), and prints the before/after with the speedup made explicit (not just raw numbers) so the improvement is obvious in class and the demo is repeatable across class sections without remembering any flag. Deliberately still reports MongoDB's own `executionStats.executionTimeMillis` (whole milliseconds) rather than a self-timed value, even though that means very fast queries can show the same rounded time before and after.
- `Faker` and `mongodb-migrations` are devcontainer-only dependencies, added to `img-backend` in `.docker/Dockerfile` the same way `boto3` was (a plain `pip3 install`, not a Lambda Layer — nothing here is ever deployed as a Lambda).

## RDS PostgreSQL instance

Stack `infrastructure/serverless/rds`: a single, publicly accessible PostgreSQL instance (`db.t4g.micro`, 20GB `gp2`, no Multi-AZ), the destination for the ETL out of MongoDB Atlas (see "ETL pipeline architecture" for the pipeline that populates it).

- **No dedicated VPC**: uses the AWS account's own default VPC (already public, with an Internet Gateway) instead of building one from scratch, via two new env vars (`DEFAULT_VPC_ID`, `DEFAULT_VPC_SUBNET_IDS`) — same "public endpoint + strong credentials, no network isolation" posture already accepted for MongoDB Atlas. RDS still requires an `AWS::EC2::SecurityGroup` (open on port 5432 to `0.0.0.0/0`) and an `AWS::RDS::DBSubnetGroup` (spanning at least 2 Availability Zones) even for a publicly accessible instance — those are the only `AWS::EC2::*` resources in the whole repo.
- **Master credentials only**, autogenerated by CloudFormation (`GenerateSecretString` + `AWS::SecretsManager::SecretTargetAttachment`, which also populates `host`/`port`/`dbname` into the same secret once the instance exists) — deliberately no separate app/read-only database user; this is a course example, not something needing least-privilege database roles.
- **No read replica, RDS Proxy, Enhanced Monitoring, Performance Insights, custom parameter group, or secrets rotation** — complexity that doesn't apply to this course's scope or free-tier budget.
- **`DeletionPolicy`/`UpdateReplacePolicy: Delete`**, not the more cautious `Snapshot` AWS defaults `AWS::RDS::DBInstance` to: a class reset (`serverless remove` + redeploy) should tear down cleanly without leaving orphaned snapshots costing storage. Automated backups (`BackupRetentionPeriod: 1`) still run day-to-day.
- Database name is `traffic_monitoring` (snake_case, the Postgres convention), deliberately different casing from Mongo's own `trafficMonitoring` database.
- **Schema lives in the default `public` schema** (kept simple — a single flat set of related tables, not a multi-domain warehouse, so a dedicated schema wasn't worth the extra indirection): dimension tables `cities`/`severities`/`roads`/`sensors` (surrogate `id` columns via `GENERATED ALWAYS AS IDENTITY`, the modern SQL-standard replacement for the older `SERIAL`) and fact tables `accident_reports`/`sensor_readings` referencing them by foreign key. `cities`/`severities` are pre-seeded by the migration itself (both are small, fixed, already-known enums — `ALLOWED_CITIES`/`SEVERITY_TRANSLATIONS`); `roads`/`sensors` start empty, populated dynamically by the Transformers (see "ETL pipeline architecture"). No PII columns on `accident_reports` — `involved_person_name`/`involved_person_id` are deliberately excluded, never decrypted into RDS. `source_s3_key`/`row_number` are `NOT NULL` (every real accident report document carries them, added by `SplitAndEnqueue`).
- `backend/src/common/postgres.py`: shared, module-level-cached connection helper (`get_connection(secret_name)`), mirroring `mongo.py`'s caching pattern but for `psycopg2`. Used by every domain's Transformer.
- **Migrations**: `backend/database/rds/` (a sibling of `backend/database/migrations/`, which is Mongo's — kept as a separate folder rather than renaming Mongo's, since that one's already tested against a real deployment). Raw SQL migration files (`migrations/<timestamp>_*.sql` + a matching `.rollback.sql`), applied via the `yoyo-migrations` PyPI package (CLI `yoyo`), unlike Mongo's migrations (Python classes via `mongodb-migrations`). `migrate.sh` resolves the RDS master secret itself (bash + `aws secretsmanager` + `jq`, URL-encoding the password), builds a `postgresql://` connection URL, and drives `yoyo apply`/`yoyo rollback` directly. Accepts an optional migration id as a second argument, passed through as `--revision` (yoyo's own flag to target one specific migration and its dependencies, confirmed against `yoyo apply --help` rather than assumed) instead of every pending/applied migration.
- **Indexes**: `accident_reports` on `(city_id, occurred_at DESC)`, `sensor_readings` on `(sensor_id, recorded_at DESC)` — the same two query patterns already indexed on the Mongo side (see "Database seeding and index migrations"), just expressed against the FK columns instead of the raw `city`/`sensor_id` values. Postgres doesn't index foreign key columns automatically (only `PRIMARY KEY`/`UNIQUE` constraints get one for free), so without these, every such lookup would be a sequential scan.

## ETL pipeline architecture

Copies both `accidentReports` and `trafficSensorReadings` from MongoDB Atlas into the RDS schema above, normalizing each document into dimension/fact rows and excluding PII — both the backfill and the live path are built and tested end to end.

Two independent, structurally identical chains, one per domain — described once below; `sensorReadings` mirrors `accidentReports` exactly, just reading `trafficSensorReadings` and writing `sensor_readings`/`sensors` instead of `accident_reports`/`roads`/`severities`.

- **Messaging infra**: stack `infrastructure/serverless/etl`: per domain, `<Domain>ExtractorQueue`, `<Domain>DispatcherQueue`, `<Domain>TransformerQueue` (each with its own DLQ) and a `<Domain>EtlTopic` (SNS). The Generator has no queue of its own (invoked directly). `<Domain>TransformerQueue` subscribes to `<Domain>EtlTopic` with a `FilterPolicy` on the `action` message attribute (`generated` for backfill, `created` for the live path) — this is the point where backfill and live-inserted data converge on the same Transformer. All names/ARNs exported to SSM for `backend/serverless/etl` and the `batch`/`streaming` stacks (which publish from the live path) to consume — this makes `batch`/`streaming` depend on `infrastructure/serverless/etl` being deployed first, the normal infra-before-backend order (unlike `alerts`, which inverts it). This pushed `alerts` to become the **last** stack deployed in the whole repo, since it's still the only one needing a `backend` stack — now `backend/serverless/batch` — already up.
- **Backend Lambdas**: stack `backend/serverless/etl` (`service: backend-etl`), only Lambdas + IAM roles (no queues/topics of its own, all referenced by SSM from the messaging infra stack above):
  1. **`<Domain>Generator`** — no event source, invoked manually (`aws lambda invoke`) to kick off a full backfill: counts documents in the Mongo collection and enqueues one `{skip, limit}` message per page (`GENERATOR_BATCH_SIZE`, default 500) onto `<Domain>ExtractorQueue`.
  2. **`<Domain>Extractor`** (SQS-triggered): for each `{skip, limit}`, reads that page from Mongo and re-queues each document individually (serialized with its Mongo `_id` as a string) onto `<Domain>DispatcherQueue`.
  3. **`<Domain>Dispatcher`** (SQS-triggered): republishes each document to `<Domain>EtlTopic` with `action=generated`.
  4. **`<Domain>Transformer`** (SQS-triggered, `batchSize: 1`): re-validates the document (defense in depth, same style as `ValidateAndPersist`/`PersistSensorReading` but without the PII checks), resolves dimension ids — `cities`/`severities` are looked up only (pre-seeded, fixed sets), `roads`/`sensors` are upserted on first sight (`backend/src/common/postgres_dimensions.py`) — and upserts the fact row (`ON CONFLICT (id) DO UPDATE`, `id` = the Mongo `_id`). Wraps the DB write in `try`/`except psycopg2.Error: connection.rollback(); raise` so a failed write can't leave the cached warm connection stuck in an aborted transaction for the next invocation. If validation fails, it self-forwards the document to its own DLQ (same pattern as `ValidateAndPersist`) — the only Lambda in the chain that does, since it's the only one with real business validation; `Generator`/`Extractor`/`Dispatcher` are glue Lambdas (like `SplitAndEnqueue`) that rely purely on SQS's own redrive-after-`maxReceiveCount` if they fail.
- **Live path**: `ValidateAndPersist` and `PersistSensorReading` each publish to their domain's `EtlTopic` (`action=created`) immediately after a successful `collection.insert_one(...)`, via the shared `backend/src/common/etl.py:publish_to_etl()` helper (extracted after `pylint`'s `duplicate-code` check flagged the two handlers' near-identical publish logic). Deliberately **best-effort**: any failure is caught and only logged, never re-raised — re-raising would make SQS redeliver the message and re-run `insert_one`, duplicating the Mongo document. The backfill chain is the safety net for anything a failed publish misses. Only a fixed subset of fields is published (`ETL_FIELDS` in each handler), matching exactly what the Extractor sends, so the Transformer can't tell live documents apart from backfilled ones — and so PII fields are never included.
- **Backfill is idempotent**: re-running a `<Domain>Generator` invocation re-processes every document, but the Transformer's `ON CONFLICT (id) DO UPDATE` means existing rows just get overwritten with the same values, never duplicated. It is **not** a sync: a document deleted from Mongo is never removed from RDS (insert/update only, no delete propagation).

## Commit convention

Base: Conventional Commits (see [reference article](https://medium.com/@iambonitheuri/the-art-of-writing-meaningful-git-commit-messages-a56887a4cb49)): types like `feat`/`fix`/`refactor`/`chore`/`docs`/`test`/etc., imperative mood, no trailing period.

**The actual style used in this repo**: each line of the message is a bullet `* <type>: <description>` (with a literal `*` at the start), one line per distinct change, even if several land in the same commit. No separate body, no additional explanation below the bullets. Real example:

```
* feat: add ValidateAndStore Lambda behind a REST API with an API key
* feat: add shared Commons Lambda layer for Python dependencies
* chore: ignore Lambda layer python/ folders in prettier, yapf and isort
* docs: update backend README deployment section for the single-stack layout
```

When a commit touches several things (code + docs, for example), reflect each one in its own bullet, don't just summarize the main one. If the changes are very different in nature, prefer several separate commits over a single commit with many unrelated bullets.

**Never add Claude co-authorship to commits in this repository.**

## Changelog convention

While the project has no release yet, `changelog.md`'s `[Unreleased]`/`[x.x.x]` entry only lists final state (`Added`/`Changed`), not internal fixes made along the way (e.g. a bug fixed before it ever shipped isn't its own `Fixed` bullet — the final, correct behavior is just what `Added` describes).
