# CLAUDE.md: Data Engineering Course

## What this project is

Batch data pipeline that ingests traffic accident reports, uploaded as an Excel file, for the traffic monitoring service described in `README.md`. This document covers the **batch** flow, the traffic sensor **streaming** flow, the **ETL** that copies both into RDS PostgreSQL, the **Bedrock Agent** that answers natural-language questions over that data, and the **chat frontend** that exposes it (all complete, see their own sections).

## How to work in this repository

Nothing from this project is installed directly on the host. All work on `backend` and `infrastructure` (installing dependencies, running the `aws` CLI, the `serverless` CLI, formatting/linting Python, deploying) happens by spinning up that subproject's Docker container (`docker compose`, using that subproject's `.docker/docker-compose.yml`) and running it there, replicating what its `entrypoint.sh` does (git configuration, `npm install`, AWS credentials from `.envs/`).

**Claude never runs deploys, `git push`, migrations against a deployed database, or other destructive/state-changing commands.** Give the command (or a read-only diagnosis, e.g. `serverless print`/`package`) and let the developer run it themselves.

## Monorepo structure

- **Root**: devcontainer for monorepo-level work (e.g. generating the architecture diagrams). `.docker/Dockerfile` is multi-stage: `img-base` (Python 3.13 + Node 24 + common tools, plus a `~/.cfnlintrc` ignoring `cfn-lint`'s W3005 false positive) → `img-backend` (adds `boto3`, only for local linter/autocomplete — never packaged, the Lambda runtime already has it) / `img-infrastructure` / `img-frontend` (identical to `img-infrastructure`) / `img-root` (adds `graphviz` + the `diagrams` library for `docs/architecture.py`).
- **`backend/`**: contains **several Serverless Framework stacks, each in its own folder under `backend/serverless/<stack>/`** (same pattern as `infrastructure/serverless/<stack>/`), not a single stack for the whole backend:
  - `backend/serverless/layers` (`service: backend-layers`): only the shared Lambda Layers, no functions of its own. **Must be deployed first**, since the other `backend` stacks consume its ARNs via SSM.
  - `backend/serverless/batch` (`service: backend-batch`): API Gateway + the batch flow's 3 Lambdas + their IAM roles.
  - Lambda code lives in `backend/src/<function_name>/` (Python, `yapf`+`isort`, see `pyproject.toml`), shared logic in `backend/src/common/`. Each `serverless.yml` (`backend/serverless/<stack>/`) references code via `../../src/...` in `package.patterns`. `handler.py` files and every migration under `backend/database/` carry no docstring — self-explanatory, kept lean; other `backend/database/` scripts (seeders, demos) do get one.
  - **`backend/src/__init__.py`** (and one in every `src/<function_name>/`) exists purely so `pylint`'s own package-boundary heuristic resolves `from src.common import ...` — not needed at runtime (Python's implicit namespace packages already resolve it without it). `pylint` is installed unpinned in the Dockerfile, and a version bump has broken this resolution project-wide before (`E0401: Unable to import 'src...'` on every handler at once); suspect that before assuming the code broke.
  - **Python dependencies go through Lambda Layers**, not a per-function `requirements.txt`: each layer lives in `backend/src/layers/<name>/` (own `requirements.txt`, generated `python/` gitignored), defined in `backend/serverless/layers/layers.yml`. Since layers live in their own stack, other stacks reference them by ARN via SSM, not `!Ref`. `entrypoint.sh` installs them locally too (into `python/` + a `.pth` file) so imports work outside Lambda.
  - **Why not `module:`**: that option changes the zip's effective root to the function's folder, clashing with `package.patterns` (relative to `serverless.yml`) and with shared code in `common/` outside it — packaging ends up empty. Lambda Layers avoid this with their own `path:` mechanism.
  - **Current layers**: `Commons` (`openpyxl`), `Mongo` (`pymongo`), `Security` (`cryptography`), `Postgresql` (`psycopg2-binary`, for the RDS ETL — see "ETL pipeline architecture"). Each Lambda only references the layers it actually needs (e.g. Lambda 1/2 don't load `Mongo` or `Security`).
  - **Secrets referenced by name, not ARN**: `custom.secretsManager.<name>` builds the name directly (e.g. `/${env:DEPLOY_APP}-secrets/MongoCredentials`), no SSM lookup. IAM still needs an ARN, built with a wildcard (`...secret:<name>-*`, covering Secrets Manager's random suffix).
  - **Deploy architecture (`x86_64`/`arm64`) is resolved dynamically**: `provider.architecture: ${file(../architecture.js):get}`, a shared script returning Node's `process.arch` — needed since `pymongo`/`cryptography` ship compiled extensions matching whoever deploys (students may be on Apple Silicon or Intel/Windows).
  - **`provider.runtime: python3.13` shows a red squiggle in every `serverless.yml`** in the `threadheap.serverless-ide-vscode` VS Code extension — known false positive (its bundled schema tops out at `python3.11` and no newer extension version fixes it). `cfn-lint`, the actual validator, is silent on it and deploys work fine — safe to ignore.
  - **Test cases**: `backend/tests/fixtures/batch/` has example Excel files + `generate_base64.sh` (generates a Postman-ready `{"file": "<base64>"}` body per file). `backend/tests/fixtures/sensor_readings/` has example MQTT payloads for the IoT Core console's test client.
- **`infrastructure/`**: shared base resources — S3, SQS+DLQ, Secrets Manager, CloudWatch alarms, RDS, the ETL's SQS+DLQ/SNS — never Lambda IAM roles (that's `backend`'s job). One sub-stack per resource (`storage`, `queue`, `secrets`, `alerts`, `rds`, `etl`), deployed independently. `serverless/queue` is general-purpose (hosts both batch's and streaming's queues+DLQs, not split per flow); `serverless/etl`'s SQS/DLQ stay separate since they're internal ETL plumbing, not an ingestion queue. All are independent **except `alerts`**, which deploys **after** `backend/serverless/batch` (its alarms reference that stack's `SplitAndEnqueue` Lambda via SSM) — the only reversal of the usual infra-before-backend order.
- **`docs/`**: architecture diagrams, one per pipeline (`architecture_batch/streaming/etl/chat.png`), generated by `docs/architecture.py` (`python3 architecture.py` in the root devcontainer, via `img-root`'s `graphviz`). Separate diagrams, not one combined view — cross-cutting edges (Mongo/Secrets Manager, shared alarms) would force long curves in Graphviz's layout; split apart, each pipeline is a straight chain. The ETL diagram draws only **one** domain's chain (`accidentReports`/`sensorReadings` are structurally identical). Diagonal (non-chain) edge labels use `xlabel`, not `label`, since `label` can leave a visible gap before the arrowhead on a long diagonal edge.
- **`frontend/`**: the chat UI subproject (see "Chat frontend") — a single stack, `serverless/site`. The batch Excel upload deliberately has no frontend and never will; tested directly via Postman. (No standalone `etl/` folder either — it's split across `backend/serverless/etl` and `infrastructure/serverless/etl`, like every flow here.)
- Each subproject (`backend`, `infrastructure`, `frontend`) has its own devcontainer, `docker-compose.yml`, `entrypoint.sh`, `.envs/config.env` (`DEVELOPER`, avoids resource-name collisions between developers) and `ws.code-workspace` (exposes the other subprojects' `.envs` too).

## Batch flow architecture

Client sends a `POST` to API Gateway with the accident Excel file encoded in **base64**, max **300 rows** per file, exposed as a REST API (not HTTP API) specifically to get API Gateway's native API Key check (`private: true` + `provider.apiGateway.apiKeys`) rejecting bad requests before the Lambda even runs.

1. **`ValidateAndStore`** (synchronous): validates structure and business rules, rejecting the whole file on any invalid row (nothing saved, 400 with the detail) rather than accepting the valid rows and dropping the rest. Excel columns are in Spanish, mapped to English for the code/Mongo:

   | Excel column                 | Field in code/Mongo    | Validation                                                                                |
   | ---------------------------- | ---------------------- | ----------------------------------------------------------------------------------------- |
   | `fecha` + `hora`             | `occurred_at`          | Combined into a single ISO 8601 timestamp                                                 |
   | `ciudad`                     | `city`                 | Bogotá, Medellín, Cali or Barranquilla                                                    |
   | `via`                        | `road`                 | Non-empty text                                                                            |
   | `severidad`                  | `severity`             | leve/moderado/grave/fatal in the Excel, translated to minor/moderate/severe/fatal on save |
   | `vehiculos_involucrados`     | `vehicles_involved`    | Integer 1-20                                                                              |
   | `nombre_persona_involucrada` | `involved_person_name` | Non-empty text (PII)                                                                      |
   | `cedula_persona_involucrada` | `involved_person_id`   | Numeric, 6-10 digits (PII)                                                                |

   `severity` is translated (leve→minor, moderado→moderate, grave→severe, fatal→fatal) before saving; `city`/`road` aren't (proper nouns). Schema/validation lives in `backend/src/common/accident_reports.py`, reused by the next two Lambdas.

2. **`SplitAndEnqueue`**, triggered by that upload's `ObjectCreated` (scoped to the `uploads/` prefix, or moving the file afterward would re-trigger it): re-parses/re-validates from S3 (Lambda 1 only passed it the raw file, not the parsed rows), splits into one SQS message per row (`source_s3_key`/`row_number` added for traceability), then moves the file to `processed/` or `failed/`. Failing here — re-validating a file Lambda 1 already accepted — is a code bug, not bad data, so it's alarmed as an `Errors` metric (see "Observability"), not routed through a DLQ.
3. **`ValidateAndPersist`** (SQS, batch size 1): re-validates (defense in depth), encrypts `involved_person_name`/`involved_person_id` (Fernet), and persists to MongoDB Atlas (Mongo client and Secrets Manager credentials both cached across warm invocations). On validation failure it self-forwards the row to the DLQ itself (with `validation_errors` attached) instead of letting SQS retry it to exhaustion — invalid data doesn't get fixed by retrying, and the DLQ message keeps the PII in plain text on purpose, so it can be corrected before a redrive. No reserved concurrency, here or anywhere in this project: the free-tier account caps out at 10 concurrent executions total, with none to spare.
4. IAM: one role per Lambda, scoped narrowly per step (S3 write / S3 read+write + SQS send / SQS receive+delete + DLQ send + the Mongo and PII-key secrets).

**Database**: MongoDB Atlas, free tier **M0** (not AWS DocumentDB: no real free tier, and would require putting the Lambdas inside a VPC).

## Streaming flow architecture

Fixed traffic sensors report average speed and vehicle count per road, every few seconds, via MQTT against **AWS IoT Core**: same shape as the batch flow, **IoT Core → SQS → Lambda → MongoDB**, with defense-in-depth validation and self-forward-to-DLQ.

**Why not Kinesis Data Streams**: no real free tier (bills per shard-hour from minute one, regardless of traffic); IoT Core does have a message free tier, and fits the sensors theme besides.

- `infrastructure/serverless/iot`: a **generic IoT Policy**, not tied to a device, using `${iot:Connection.Thing.ThingName}` so a certificate can only connect/publish on its own topic (`sensors/traffic/<thing-name>/data`); a Topic Rule (`SELECT *, topic(3) AS thing_name ...`) stamps the sensor's identity onto the message straight from that trusted topic segment — the sensor's own JSON payload carries no `sensor_id` at all, precisely so there's nothing client-controlled to trust instead.
- `PersistSensorReading` (`backend/serverless/streaming`) sets `sensor_id` from that trusted `thing_name` before validating. No PII in a reading (`city`, `road`, `speed_avg`, `vehicle_count`, `recorded_at`), so no encryption/`Security` layer. Shares `backend/src/common/mongo.py`'s connection-caching helper with batch's Lambda 3.
- Provisioning/testing a real sensor: `backend/tests/sensor_readings/provision_sensor.sh <sensor-id>` (Thing + X.509 cert, idempotent per sensor) and `send_sensor_reading.sh <sensor-id> [file] [topic]` (`mosquitto_pub` with mTLS). Confirmed one sensor's certificate can't publish on another's topic (blocked by the Policy — verified nothing arrived when subscribed to that topic from the console). `mosquitto_pub -i` must match the certificate's Thing name, or the connection drops immediately ("connection was lost").

## Observability

Stack `infrastructure/serverless/alerts`: an SNS topic with an email subscription (`ALERTS_EMAIL`, needs the subscription confirmed the first time the stack is deployed) receives three CloudWatch alarms:

- Visible messages in the accident reports DLQ (`ApproximateNumberOfMessagesVisible >= 1`): indicates rows Lambda 3 couldn't validate/process.
- Errors in Lambda 2 (`SplitAndEnqueue`, `Errors` metric >= 1): indicates it failed re-validating a file Lambda 1 had already accepted, a symptom of a bug in the code itself (see point 2 of the batch flow architecture).
- Visible messages in the sensor readings DLQ (`ApproximateNumberOfMessagesVisible >= 1`, same criterion as accidents'): indicates readings `PersistSensorReading` couldn't validate/process.

There's no alarm on Lambda 1 or Lambda 3 errors: Lambda 1 responds its errors directly to the client via API Gateway (synchronous), and Lambda 3's invalid rows go to the DLQ (already covered by the alarm above) instead of raising an exception. Streaming has no step equivalent to Lambda 2 (IoT Core routes straight to the queue with no intermediate re-validation), so it doesn't have that second "bug in the code" alarm either.

The same stack also defines an **AWS Budget on cost** (`AWS::Budgets::Budget`, USD 1/month, notifies by email on both actual and forecasted spend): unlike the CloudWatch alarms (scoped to this pipeline), the Budget covers spend for **the whole AWS account**, meant to catch anything that fell outside the free tier. "Free Tier Alerts" (a Billing account preference, not an IaC resource, that would warn before any real charge) was deliberately not also turned on: it was considered and dropped as redundant next to the Budget, for this project's scope.

## Database seeding and index migrations

`backend/database/` (not IaC — MongoDB Atlas itself isn't managed by any IaC tool in this project, its M0 cluster is created manually):

- `backend/database/seeders/seed_mongo.py` + `seed.sh`: fills `accidentReports`/`trafficSensorReadings` with realistic synthetic data (`Faker` + a curated list of real road names per city), reusing the real validation and PII encryption so seeded documents look indistinguishable from real ones — including `source_s3_key`/`row_number`, simulated in `MAX_ROWS` batches. Feeds the ETL to RDS PostgreSQL and, from there, the Bedrock agent. Refuses to run unless `MongoCredentials`'s `STAGE` tag is `dev`/`test`. Inserts in `INSERT_BATCH_SIZE` (500) batches, not one giant `insert_many` — an Atlas M0 connection can't handle tens of thousands of documents in one call.
- `backend/database/migrations/`: index management via `mongodb-migrations` (CLI `mongodb-migrate`). Migration files (`migrations/migrations/<timestamp>_*.py`) implement `BaseMigration`'s `upgrade`/`downgrade`, calling `create_index`/`drop_index` via the shared `mongo.get_collection` helper. `migrate.sh` resolves the Mongo secret itself and exports `PYTHONPATH` (needed since `mongodb-migrate` loads migrations via a raw `__import__()`, not `python3 -m`). An optional timestamp argument (`--to_datetime`) targets one migration instead of all of them. Applied migrations are tracked in an auto-created `migrationLogs` collection.
- Current indexes: `accidentReports` on `(city, occurred_at)`, `trafficSensorReadings` on `(sensor_id, recorded_at)` — chosen to match the two most natural query patterns ("accidents in city X, most recent first" / "readings for sensor X, ordered by time").
- `backend/database/demo_indexes.py`: the classroom demo. Always reverts every index first (`migrate.sh --downgrade`, unconditional — a real before/after is the only point), runs `explain()` before the index exists (`COLLSCAN`), re-applies _only that collection's_ migration, runs `explain()` again (walking into `inputStage` for the real `IXSCAN`, since Mongo often wraps it in `FETCH`), and prints the speedup explicitly. Reports MongoDB's own `executionTimeMillis` rather than a self-timed value, even though fast queries can round to the same number before/after.
- `Faker` and `mongodb-migrations` are devcontainer-only (`pip3 install` in `img-backend`, like `boto3`) — nothing here ever deploys as a Lambda.

## RDS PostgreSQL instance

Stack `infrastructure/serverless/rds`: a single, publicly accessible PostgreSQL instance (`db.t4g.micro`, 20GB `gp2`, no Multi-AZ), the destination for the ETL out of MongoDB Atlas (see "ETL pipeline architecture" for the pipeline that populates it).

- **No dedicated VPC**: uses the account's own default VPC (already public, via env vars `DEFAULT_VPC_ID`/`DEFAULT_VPC_SUBNET_IDS`) — same "public endpoint + strong credentials, no network isolation" posture as MongoDB Atlas. Still needs an `AWS::EC2::SecurityGroup` (open on 5432 to `0.0.0.0/0`) and a `DBSubnetGroup` (2+ AZs) — the only `AWS::EC2::*` resources in the repo.
- **Master credentials only**, autogenerated by CloudFormation (`GenerateSecretString` + `SecretTargetAttachment`, which also fills in `host`/`port`/`dbname`) — deliberately no separate app user; a course example, not needing least-privilege roles.
- **No read replica, RDS Proxy, Enhanced Monitoring, Performance Insights, or secrets rotation** — complexity that doesn't apply to this course's scope or free-tier budget.
- **`DeletionPolicy`/`UpdateReplacePolicy: Delete`**, not AWS's default `Snapshot`: a class reset (`serverless remove` + redeploy) should tear down cleanly without orphaned snapshots costing storage. Automated backups (`BackupRetentionPeriod: 1`) still run day-to-day.
- Database name is `traffic_monitoring` (snake_case, the Postgres convention), deliberately different casing from Mongo's own `trafficMonitoring` database.
- **Schema lives in the default `public` schema** (a single flat set of tables, no multi-domain warehouse needed): dimension tables `cities`/`severities`/`roads`/`sensors` (`GENERATED ALWAYS AS IDENTITY`, not `SERIAL`) and fact tables `accident_reports`/`sensor_readings` by foreign key. `cities`/`severities` are pre-seeded by the migration (fixed enums); `roads`/`sensors` start empty, populated by the Transformers. No PII columns on `accident_reports` — `involved_person_name`/`involved_person_id` are excluded, never decrypted into RDS. `source_s3_key`/`row_number` are `NOT NULL` (every real document carries them, added by `SplitAndEnqueue`).
- `backend/src/common/postgres.py`: shared, module-level-cached connection helper (`get_connection(secret_name)`), mirroring `mongo.py`'s caching pattern but for `psycopg2`. Used by every domain's Transformer.
- **Migrations**: `backend/database/rds/` (a sibling of Mongo's `backend/database/migrations/`, kept separate rather than renamed). Raw SQL files (`migrations/<timestamp>_*.sql` + `.rollback.sql`), applied via `yoyo-migrations` (CLI `yoyo`), unlike Mongo's Python-class migrations. `migrate.sh` resolves the RDS master secret, builds a `postgresql://` URL, and drives `yoyo apply`/`rollback`. An optional migration id (`--revision`) targets one migration instead of every pending/applied one.
- **Indexes**: `accident_reports` on `(city_id, occurred_at DESC)`, `sensor_readings` on `(sensor_id, recorded_at DESC)` — same two query patterns as the Mongo side, against the FK columns. Postgres doesn't index foreign keys automatically, so without these every such lookup is a sequential scan.
- **Parameter group + `pg_cron`**: the one custom `DBParameterGroup` in the project (`shared_preload_libraries: pg_cron`) — `pg_partman` recommends scheduling its maintenance via `pg_cron`, not an external scheduler. `shared_preload_libraries` is static: changing it on a running instance needs a reboot; a fresh deploy doesn't.
- **`sensor_readings` is partitioned** (`PARTITION BY RANGE (recorded_at)`, one partition per day via `pg_partman`'s `create_parent()`) — the only partitioned table, since it's the one growing continuously. Its primary key is `(id, recorded_at)`, not just `id`, since Postgres requires unique constraints on a partitioned table to include the partition key (safe, `recorded_at` never changes post-insert). A `pg_cron` job runs `partman.run_maintenance_proc()` daily at 3 AM to keep 4 days of future partitions premade; no retention policy, so old partitions are never dropped.
- `backend/database/rds/demo_partitioning.py`: the partitioning demo, mirroring `demo_indexes.py`'s before/after style — but toggles Postgres' `enable_partition_pruning` setting instead of the migration itself, since undoing partitioning would mean dropping the table and a full ETL backfill.

## ETL pipeline architecture

Copies both `accidentReports` and `trafficSensorReadings` from MongoDB Atlas into the RDS schema above, normalizing each document into dimension/fact rows and excluding PII — both the backfill and the live path are built and tested end to end.

Two independent, structurally identical chains, one per domain — described once below; `sensorReadings` mirrors `accidentReports` exactly, just reading `trafficSensorReadings` and writing `sensor_readings`/`sensors` instead of `accident_reports`/`roads`/`severities`.

- **Messaging infra**: stack `infrastructure/serverless/etl`: per domain, `<Domain>ExtractorQueue`/`DispatcherQueue`/`TransformerQueue` (each with a DLQ) and a `<Domain>EtlTopic` (SNS). The Generator has no queue (invoked directly). `TransformerQueue` subscribes to `EtlTopic` with a `FilterPolicy` on `action` (`generated` for backfill, `created` for live) — where both paths converge on the same Transformer. Names/ARNs export to SSM for `backend/serverless/etl` and `batch`/`streaming` (which publish from the live path) — making them depend on this stack first, the normal infra-before-backend order (unlike `alerts`, which inverts it and became the **last** stack deployed in the repo).
- **Backend Lambdas**: stack `backend/serverless/etl` (`service: backend-etl`), only Lambdas + IAM roles (no queues/topics of its own, all referenced by SSM from the messaging infra stack above):
  1. **`<Domain>Generator`** — no event source, invoked manually (`aws lambda invoke`) to kick off a full backfill: counts documents in the Mongo collection and enqueues one `{skip, limit}` message per page (`GENERATOR_BATCH_SIZE`, default 500) onto `<Domain>ExtractorQueue`.
  2. **`<Domain>Extractor`** (SQS-triggered): for each `{skip, limit}`, reads that page from Mongo and re-queues each document individually (serialized with its Mongo `_id` as a string) onto `<Domain>DispatcherQueue`.
  3. **`<Domain>Dispatcher`** (SQS-triggered): republishes each document to `<Domain>EtlTopic` with `action=generated`.
  4. **`<Domain>Transformer`** (SQS-triggered, `batchSize: 1`): re-validates the document (same defense-in-depth style as `ValidateAndPersist`/`PersistSensorReading`, minus PII checks), resolves dimension ids (`cities`/`severities` looked up only; `roads`/`sensors` upserted on first sight via `postgres_dimensions.py`), and upserts the fact row (`ON CONFLICT (id) DO UPDATE`, `id` = the Mongo `_id`). Wraps the DB write in `try`/`except psycopg2.Error: connection.rollback(); raise` so a failed write can't leave the warm connection stuck mid-transaction. Self-forwards to its own DLQ on validation failure — the only Lambda in the chain with real business validation; `Generator`/`Extractor`/`Dispatcher` just rely on SQS's own redrive-after-`maxReceiveCount`.
- **Live path**: `ValidateAndPersist`/`PersistSensorReading` publish to their domain's `EtlTopic` (`action=created`) right after `insert_one(...)`, via the shared `etl.py:publish_to_etl()` helper. Deliberately **best-effort**: failures are caught and only logged, never re-raised (re-raising would redeliver via SQS and duplicate the insert) — the backfill chain is the safety net. Only a fixed field subset (`ETL_FIELDS`) is published, matching the Extractor's output, so the Transformer can't tell live from backfilled documents, and PII is never included.
- **Backfill is idempotent**: re-running a `<Domain>Generator` re-processes every document, but `ON CONFLICT (id) DO UPDATE` just overwrites existing rows, never duplicates. **Not** a sync: a document deleted from Mongo is never removed from RDS.

## Bedrock Agent (AgentCore)

Stack `backend/serverless/bedrock` (`service: backend-bedrock`): an agent that answers natural-language questions about the traffic monitoring data by generating and running SQL against RDS. Exposed through a chat frontend (see "Chat frontend" below), and still invocable directly via the AgentCore API/SDK for testing.

- **Built on Amazon Bedrock AgentCore, not "Agents for Amazon Bedrock"**: the classic `AWS::Bedrock::Agent` API entered maintenance mode on July 30, 2026 and stopped accepting new accounts with no prior usage (confirmed via CloudTrail's `CreateAgent` `AccessDenied` message). AgentCore is AWS's recommended migration path.
- **Resource chain** (one hop more than the classic Agent had): `AWS::BedrockAgentCore::Harness` (the agent: model, system prompt, tools, memory) → a `Tool` of type `agentcore_gateway` → `AWS::BedrockAgentCore::Gateway` (connectivity layer, `AuthorizerType: AWS_IAM` since only the Harness calls it, never an end user) → `AWS::BedrockAgentCore::GatewayTarget` (`TargetConfiguration.Mcp.Lambda`, pointing at `RunSqlQueryLambdaFunction` with an inline `ToolSchema`).
- **Three roles, and the Harness's is much bigger than it looks like it should be**: the Gateway's role only needs `lambda:InvokeFunction` on the Lambda (identity-based, not a Lambda resource policy like the classic Action Group needed). The Lambda's role is unchanged (`readonly` Postgres credentials). The **Harness's role** needs far more: `bedrock-agentcore:GetWorkloadAccessToken`/`GetWorkloadAccessTokenForJWT` (workload identity, to start a session), CloudWatch Logs (scoped to `/aws/bedrock-agentcore/runtimes/*`), X-Ray tracing, and `ecr-public:GetAuthorizationToken`/`sts:GetServiceBearerToken` (pulls its own container image from ECR Public every session) — without these it can't even start. Both trust policies are the **unconditioned** `Principal: bedrock-agentcore.amazonaws.com` `sts:AssumeRole` — a `Condition` on `aws:SourceAccount`/`aws:SourceArn` (like the classic Agent needed) makes `CreateHarness`/`CreateGateway` fail.
- **`HarnessName` has a stricter pattern than every other name in this project** (`^[a-zA-Z][a-zA-Z0-9_]{0,39}$` — no hyphens, 40 chars max), so it's a fixed literal (`TrafficMonitoringAgent`), not built from `servicePrefix` like everything else. Same for the `Memory` resource's `Name` (48 chars max, still no hyphens).
- **One generic tool, real text-to-SQL**: a single `run_sql_query(sql)` tool — the model writes the full SQL itself (schema described statically in the system prompt), not curated per-question tools. The prompt also sets tone (formal, brief, no emojis, polite even if the user isn't) and refuses out-of-scope questions. `MaxIterations: 5` caps the generate→error→retry loop per invocation, well within `TimeoutSeconds: 900` — the Lambda's own 15s `timeout` is the tighter constraint to watch.
- **Conversation memory**: a dedicated `AWS::BedrockAgentCore::Memory` resource (not the Harness's "managed memory" convenience option) with `MemoryStrategies` deliberately omitted — short-term only (raw messages per session, keyed by `runtimeSessionId`/`actorId`), no long-term strategies (their own extraction/storage cost, and this agent doesn't need cross-session recall). Omitting the Harness's `Memory` property entirely would have silently provisioned managed memory _with_ long-term strategies by default (the API's default differs from the CLI's, which disables it) — deliberate, not an oversight.
- **Model**: Claude Haiku via a cross-region inference profile (`us.anthropic.claude-haiku-4-5-20251001-v1:0`) — recent Claude models reject the bare foundation-model ID for on-demand invocation. IAM needs `bedrock:InvokeModel`/`InvokeModelWithResponseStream`/`GetInferenceProfile`/`GetFoundationModel`, scoped to both the inference-profile and foundation-model ARNs.
- **`RunSqlQuery` Lambda** (`backend/src/run_sql_query/handler.py`): AgentCore's own event/response contract (flat `{"sql": "..."}` in, plain dict out — no Action Group envelope). Connects via the `readonly` Postgres role (see "RDS PostgreSQL instance"), rejects anything not starting with `SELECT`/`WITH`, forces/caps a `LIMIT`, and sets `statement_timeout` — defense in depth since a read-only query can still be a slow full scan. Returns `{"error": "..."}` instead of raising, so the agent can see the error and retry.
- **Prerequisite that IaC can't cover**: Claude Haiku's model access must be enabled for the account/region in the Bedrock console before the agent can actually invoke it — an account-level toggle, not a CloudFormation resource.
- **Testing without writing code**: the AWS Console has a Harness Playground (Amazon Bedrock → AgentCore → Harness → Playground tab) — pick a harness from a dropdown and chat with it interactively; confirmed working against this CloudFormation-created Harness too.

## Chat frontend

A top-level subproject, `frontend/` (same devcontainer/`.envs`/`ws.code-workspace` pattern as `backend`/`infrastructure` — see "Monorepo structure"), gives the Bedrock agent a real UI instead of only the console Playground or a raw SDK call.

- **`backend/serverless/bedrock` gained a `ChatStream` Lambda** behind a native WebSocket API (no plugin needed — `events: - websocket: {route: ...}` is built into Serverless Framework). `$connect`/`$disconnect` are no-ops (no connection state persisted anywhere — each `sendMessage` is self-contained, carrying its own `sessionId`); `sendMessage` calls `bedrock-agentcore:InvokeHarness` with the client-supplied `sessionId`/`prompt`, then relays the stream back via `apigatewaymanagementapi.post_to_connection`. IAM needs both `InvokeHarness` _and_ `InvokeAgentRuntime`, both scoped to `!GetAtt Agent.Arn` — the latter is easy to miscope against the Harness's underlying `Environment.AgentCoreRuntimeEnvironment.AgentRuntimeArn` instead, which throws `AccessDeniedException` at invoke time.
- **Message protocol** (JSON over the WebSocket): client → server is `{"action": "sendMessage", "sessionId": "...", "prompt": "..."}` (`action` matches Serverless Framework's default `$request.body.action` route selection). Server → client is `{"type": "tool_start"}` (agent starts calling `run_sql_query`), `{"type": "delta", "text": "..."}` (one chunk per `contentBlockDelta`), or `{"type": "done"}` — each carrying its `sessionId` so the frontend can route it, since multiple conversations share one WebSocket connection.
- **`frontend/serverless/site`** (`service: frontend-site`): a private S3 bucket (same posture as `RawReportsBucket`) behind CloudFront via **Origin Access Control** — the current AWS-recommended pattern, not public website hosting (`OriginAccessControlId` sits on the `Origin`, sibling to `S3OriginConfig`, whose `OriginAccessIdentity` stays empty). No custom domain/ACM cert — the default `*.cloudfront.net` already gives free HTTPS, which the WebSocket connection needs. `CachePolicyId` uses AWS's managed `CachingOptimized` policy (`658327ea-f89d-4fab-a63d-7e88639e58f6`).
- **The deploy uploads the site too, with no Serverless Framework plugin**: `serverless-s3-sync` exists but is unmaintained and doesn't handle CloudFront invalidation either — not worth it over one `aws s3 sync` call. `deploy.sh` resolves `backend-bedrock`'s `ChatWebSocketUrl` SSM parameter, writes `dist/config.js` with it (`window.CHAT_CONFIG = {...}`, loaded before `app.js` — a plain injected file, no build tooling), copies `src/` into `dist/`, runs `serverless deploy`, then `aws s3 sync` and `aws cloudfront create-invalidation` — same "bash script wrapping AWS CLI" style as `migrate.sh`/`seed.sh`. Must deploy **after** `backend/serverless/bedrock` (same reversed-order precedent as `alerts`).
- **Frontend is intentionally minimal**: vanilla HTML/CSS/JS, no framework, no build step. All state lives in an in-memory array in the browser tab — reloading loses everything, no reconnection logic if the socket drops. Multiple conversations can run at once (sidebar + "Nueva conversación"), multiplexed over one shared WebSocket connection, disambiguated by `sessionId`.
- **Doesn't cover the batch Excel upload** — that flow deliberately has no frontend and never will; it's tested directly via Postman.

## Commit convention

Base: Conventional Commits (see [reference article](https://medium.com/@iambonitheuri/the-art-of-writing-meaningful-git-commit-messages-a56887a4cb49)): types like `feat`/`fix`/`refactor`/`chore`/`docs`/`test`/etc., imperative mood, no trailing period.

**The actual style used in this repo**: each line of the message is a bullet `* <type>: <description>` (with a literal `*` at the start), one line per distinct change, even if several land in the same commit. No separate body, no additional explanation below the bullets. Real example:

```text
* feat: add ValidateAndStore Lambda behind a REST API with an API key
* feat: add shared Commons Lambda layer for Python dependencies
* chore: ignore Lambda layer python/ folders in prettier, yapf and isort
* docs: update backend README deployment section for the single-stack layout
```

When a commit touches several things (code + docs, for example), reflect each one in its own bullet, don't just summarize the main one. If the changes are very different in nature, prefer several separate commits over a single commit with many unrelated bullets.

**Never add Claude co-authorship to commits in this repository.**

## Changelog convention

`changelog.md`'s top two headings are `## [Unreleased]` followed by `## [x.x.x] - dd/mm/yyyy`, and they serve different purposes:

- **`[Unreleased]`** is a backlog: things that are done (built, maybe even committed) but deliberately paused/not deployed yet, kept there so they aren't forgotten. Not always empty.
- **`[x.x.x] - dd/mm/yyyy`** is the actual next release in progress — its bullets, under whichever standard Keep a Changelog category applies (`### Added`, `### Changed`, `### Fixed`, `### Removed`, etc. — not just `Added`/`Changed`), are what's actively being worked toward shipping, with `x.x.x`/`dd/mm/yyyy` as a placeholder for whatever version/date it turns out to be once released.

Both only list final state, not internal fixes made along the way **before** something ever shipped (e.g. a bug introduced and fixed within the same unreleased cycle isn't its own `Fixed` bullet — the final, correct behavior is just what `Added` describes). A real `Fixed` bullet is for a bug in something from a _previous_, already-released version.
